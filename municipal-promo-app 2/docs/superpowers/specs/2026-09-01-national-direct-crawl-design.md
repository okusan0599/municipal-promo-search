# 全国自治体公式公示ページ直接収集 v6 設計

## 目的

現行 v5.1 の「官公需情報ポータルサイト検索API」を全国横断の入口として維持しながら、47都道府県庁・全国市町村・東京23特別区の公式Webサイトから、入札・契約・公募・プロポーザル・企画提案等の公示を直接収集する第二経路を追加する。

検索UIは現行の電通関連度・領域分類・地域・都道府県・予算・日付・キーワード絞り込みを維持し、公式自治体ソースから取得した案件も同じデータモデルで検索できるようにする。

## 対象範囲

### 対象自治体

- 47都道府県庁
- 全国の市・町・村
- 東京23特別区
- 政令指定都市は「市」を1自治体として扱う
- 政令指定都市の行政区は独立した発注自治体としては扱わない
- 観光協会、DMO、第三セクター、公社、外郭団体は v6 の対象外とし、次段階で追加する

自治体数はマスター生成時点の公的自治体コード一覧に従い、固定件数をコード内に埋め込まない。

### 対象公示

- 入札・契約情報
- 業務委託
- 公募
- 公募型プロポーザル
- 企画提案・提案競技
- コンペ
- 仕様書・募集要領を伴う委託案件
- 自治体の新着情報にしか掲載されない対象案件

物品購入・工事等もクロール時には候補として取得しうるが、現行の電通フィット分類で低関連に落とし、デフォルト検索から除外する。

## 全体アーキテクチャ

```text
官公需API --------------------┐
                              │
自治体マスター                │
  ↓                           │
公式サイトURL                 │
  ↓                           │
公示ページ探索                │
  ↓                           │
定期クロール                  │
  ↓                           │
案件候補抽出                  │
  ↓                           │
本文・添付資料解析            │
  ↓                           │
正規化 / 重複統合 ------------┤
  ↓                           │
電通フィット分類              │
  ↓                           │
PostgreSQL <------------------┘
  ↓
FastAPI
  ↓
現行検索UI
```

Webサーバーとクロール処理は分離する。Render Web Service の起動時や `/api/projects` リクエスト中には全国クロールを行わない。

## コンポーネント

### 1. 自治体マスター

PostgreSQL `municipalities` テーブルに以下を保持する。

- `code`: 自治体コード
- `prefecture`: 都道府県名
- `name`: 自治体名
- `kind`: prefecture / city / ward / town / village
- `official_url`: 公式トップURL
- `official_host`: 公式ホスト名
- `area`: 北海道 / 東北 / 北関東 / 南関東 / 甲信越 / 北陸 / 東海 / 近畿 / 中国 / 四国 / 九州 / 沖縄
- `active`: 現行自治体か
- `last_verified_at`: 公式URL最終確認日時

自治体コード・名称の基礎マスターは公的データから生成する。公式URLは実行時にJ-LISへ依存せず、事前生成した静的シードをDBへ投入する。J-LIS等を利用して公式URLを更新する場合も、運用Webプロセスからは直接取得しない。

### 2. 公式公示ソースマスター

`municipal_sources` テーブルに1自治体あたり複数の公式ページを保持する。

- `municipality_id`
- `source_type`: procurement / proposal / public_call / outsourcing / news / other
- `url`
- `title`
- `discovery_method`: seed / sitemap / link_discovery / manual
- `priority`: 1〜5
- `active`
- `robots_allowed`
- `last_success_at`
- `last_failure_at`
- `failure_count`
- `etag`
- `last_modified`
- `content_hash`
- `next_crawl_at`

唐津市の `https://www.city.karatsu.lg.jp/site/nyusatsu/` は `procurement` ソースとして登録される。

### 3. 公示ページ自動探索

公式トップURLから、以下の順で公示ソース候補を探索する。

1. 既知シードURL
2. `sitemap.xml` / sitemap index
3. 公式トップ・主要メニューの同一ドメインリンク
4. URL・アンカーテキストをキーワードスコアリング

高優先キーワード:

- 入札
- 契約
- 調達
- 公募
- プロポーザル
- 企画提案
- 提案競技
- 業務委託

探索は同一公式ホストを基本とし、自治体が利用する公式サブドメイン・公式調達システムへの外部リンクは明示的な許可リストで扱う。

1自治体の探索上限を設け、サイト全体を無制限に巡回しない。

### 4. 定期クロール

Render Web Service とは別の Cron Job で実行する。

- `python -m app.jobs.crawl_due_sources`
- DBから `next_crawl_at <= now()` のソースを優先度順に取得
- 1回のジョブで一定件数だけ処理
- 成功時は `next_crawl_at` を更新
- 失敗時は指数バックオフ
- ETag / Last-Modified / content hash で未変更ページの再解析を抑制

初期値:

- 高優先ソース: 6時間ごと
- 通常ソース: 24時間ごと
- 新着ページ: 12時間ごと
- 失敗ソース: 6h → 12h → 24h → 72h のバックオフ
- 同一ホストへの最小アクセス間隔: 2秒
- HTTPタイムアウト: 15秒
- robots.txtを尊重

### 5. 候補案件リンク抽出

一覧ページから以下のアンカーを候補化する。

- 公募中
- プロポーザル
- 企画提案
- 業務委託
- 入札公告
- 募集要領
- 実施要領
- 仕様書

一覧ページのナビゲーション・カテゴリリンク・過去年度アーカイブはスコアを下げる。

候補詳細ページは、自治体公式ホストまたは明示的に許可された公式外部調達システムのみ追跡する。

### 6. 本文・添付資料解析

詳細ページHTMLから以下を抽出する。

- 案件名
- 発注自治体 / 部署
- 公示日
- 参加申込期限
- 質問期限
- 企画提案書提出期限
- プレゼン / 審査日
- 予算 / 上限額
- 契約期間
- 概要
- 原公示URL
- 添付資料URL

HTML本文を優先し、PDF・Word添付は必要な項目がHTMLにない場合に解析する。PDF等は収集元URLを保持し、原則としてユーザー向けに再配布しない。

### 7. 重複統合

`projects` と `project_sources` を分離する。

同一案件候補は以下で照合する。

- 自治体コード
- 正規化した案件名
- 提出期限
- 公示日
- 原公示URL

優先順位:

1. 自治体公式詳細ページ
2. 自治体公式一覧ページ
3. 官公需情報ポータル

同一案件に複数ソースがある場合は、公式ページの値を主値として採用し、官公需APIは補助値とする。

### 8. 電通フィット分類

現行 v5.1 の分類器を共通利用する。

- コンサル・戦略策定
- 広報・PR・コミュニケーション
- 広告・クリエイティブ
- SNS・デジタルマーケティング
- メディア・コンテンツ・動画
- イベント・体験設計
- 観光・地域ブランディング
- 調査・マーケティング
- Web・アプリ・デジタルサービス
- AI・データ活用・DX
- ブランディング・VI/CI

分類対象には、自治体サイトの共通ナビゲーションやJavaScriptを含めず、案件名・案件本文主要部・仕様書要旨を使う。

### 9. 検索API

`GET /api/projects` はPostgreSQLから検索する。

既存互換フィールドを維持しつつ、以下を追加する。

- `sourceSystem`: `municipality_direct` / `kkj`
- `sourceCount`
- `officialSourceUrl`
- `lastChecked`
- `municipalityCode`
- `dataQuality`

フロントエンドは現行v5.1のフィルタを維持し、データ取得元の違いを意識せず検索できる。

### 10. 管理・観測API

ユーザー向け検索とは別に、運用確認用の軽量APIを持つ。

- `/api/admin/source-stats`
- `/api/admin/crawl-status`
- `/api/admin/municipality-coverage`

表示項目:

- 自治体総数
- 公式URL確認済み数
- 公示ソース発見済み自治体数
- 24時間以内に成功したソース数
- 失敗ソース数
- 新規案件数
- 官公需のみ / 公式直接のみ / 両方の案件数

認証なしで詳細な内部エラーやDB接続情報は返さない。

## PostgreSQL テーブル

最低限以下を作る。

- `municipalities`
- `municipal_sources`
- `crawl_runs`
- `source_fetches`
- `projects`
- `project_sources`

JSON文字列だけで全てを保存せず、検索・重複判定に使う主要項目は正規カラムにする。

## 更新フロー

### 初期導入

1. 自治体マスターを投入
2. 公式トップURLシードを投入
3. 既知の公示ページシードを投入
4. ソース探索ジョブを分割実行
5. 発見した公示ページを保存
6. クロールジョブ開始
7. 官公需キャッシュをDBへ移行
8. APIをDB読み取りへ切替

### 定常運用

1. due sourceを取得
2. robots / レート制限確認
3. 条件付きGET
4. 変更ありなら案件リンク抽出
5. 詳細解析
6. upsert / dedupe
7. 電通フィット再分類
8. 次回クロール時刻更新

## エラー処理

- 1自治体の失敗でジョブ全体を失敗させない
- HTTP 403/429は長めのバックオフ
- 404はソース再探索対象
- 5xx/timeoutは短期再試行後にバックオフ
- robots禁止はクロールせず記録
- JSレンダリング必須ページは `needs_browser=true` として別キューへ送るが、v6初版ではPlaywright自動実行を必須にしない
- PDF解析失敗でもHTMLから取得できた案件は保存する

## セキュリティ / 運用

- `DATABASE_URL`、管理トークン等はRender Environment Variablesに保存
- GitHubへ秘密情報を書かない
- DBはWeb Serviceと同一リージョンを基本にする
- 公開済み自治体情報のみを保存対象とする
- 管理APIに個人情報・社内営業情報を持たせない
- 原文PDFの再配布を前提にせずURL参照を基本とする

## 性能・負荷方針

全国サイトを一斉にクロールしない。Cron Jobは「期限到来ソースを少量ずつ」処理する。

Web検索リクエスト中に外部自治体サイトへアクセスしないため、検索画面の速度はクロール速度に依存しない。

## v6 初版の完了条件

- Web Service起動時に全国クロールを開始しない
- PostgreSQLから現行UIが検索できる
- 官公需API案件と公式直接案件を同じ一覧で表示できる
- 自治体マスターを全対象自治体分保持できる
- 唐津市を含む代表fixtureで直接収集が成功する
- 公式URL・ソースURL・最終取得日時を案件で確認できる
- ジョブ失敗が検索画面を停止させない
- 公式サイト直接収集のカバレッジを管理APIで可視化できる

## 段階導入

### Phase A: 基盤

PostgreSQL、テーブル、DBリポジトリ、官公需データ移行、検索API切替。

### Phase B: 直接収集

自治体マスター、ソース探索、HTML収集、案件抽出、重複統合。

### Phase C: 全国展開

全自治体公式URLシード投入、分割ソース探索、Cron運用、失敗自治体の再探索。

### Phase D: 精度改善

PDF/Word解析強化、JS必須サイト対応、自治体別アダプタ、外郭団体追加。

## 非目標

v6初版では以下を必須としない。

- 全自治体100%の初日カバレッジ
- ログイン付き社内CRM
- 提案書管理
- 落札企業・契約結果の完全追跡
- 外郭団体・DMO・観光協会の網羅
- Playwrightによる全サイトブラウザレンダリング

全国の公式サイト構造は統一されていないため、v6は「全対象自治体を管理対象にし、直接収集カバレッジを継続的に高められる基盤」を完成条件とする。
